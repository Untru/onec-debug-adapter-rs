# Проект в разработке. 



# onec-debug-adapter-rs

Нативный кроссплатформенный адаптер [Debug Adapter Protocol][dap] для HTTP-сервера отладки 1С:Предприятия. Цель проекта — не требовать от пользователя .NET, Java, Node.js или прав администратора: распространяются готовые бинарники для каждой платформы.

Проект является независимой реализацией протокола. HTTP/XML-интерфейс сервера отладки изучался по открытому проекту [akpaevj/onec-debug-adapter][reference], выпущенному под MIT.

## Статус

Реализована рабочая нативная основа отладки через RDBG:

- DAP `launch`, `attach`, breakpoints, exception breakpoints, stepping, pause, threads и disconnect;
- source/condition/hit-count/logpoint для BSL-модулей основной конфигурации и расширений;
- событие остановки, stack trace, раскрываемые локальные variables и evaluate/hover, включая отложенный RDBG `exprEvaluated`;
- панель «Цели отладки» в VS Code: список доступных 1С-сеансов, ручное подключение и обновление списка при старте/завершении цели;
- `launch` выбирает `1cv8c` из `platformPath` (указанная версия или `LATEST`) и запускает его с HTTP-отладкой; для файловой базы сам поднимает и затем останавливает `dbgs`, используя выделенный им порт;
- CI проверяет форматирование, Clippy, unit-тесты и упаковку VSIX.

`attach` предназначен для уже доступного сервера отладки 1С. Для `launch` платформа 1С должна быть установлена у пользователя, но Rust, .NET, Node.js и права администратора для адаптера не нужны.

## Локальная сборка

Для разработки нужен Rust 1.85 или новее. У конечного пользователя Rust не нужен:

```sh
cargo build --release
```

Получившийся файл: `target/release/onec-debug-adapter` (`.exe` в Windows). Пример конфигурации находится в [`examples/launch.json`](examples/launch.json).

При публикации тега `v*` GitHub Actions собирает нативные VSIX для Windows x64, Linux x64/ARM64 и macOS x64/Apple Silicon. В каждом VSIX находится только подходящий бинарник адаптера; устанавливать .NET, Rust или Node.js пользователю не нужно.

## Установка VSIX

1. На странице [GitHub Releases](https://github.com/Untru/onec-debug-adapter-rs/releases) скачайте файл `onec-debug-native-<target>.vsix` для своей ОС и архитектуры.
2. В VS Code откройте **Extensions**, нажмите `…` и выберите **Install from VSIX…**. Либо выполните:

   ```sh
   code --install-extension onec-debug-native-<target>.vsix
   ```

3. В палитре команд VS Code запустите **«1C: Настроить отладку…»**. Это интерактивный мастер: он показывает только пригодные для запуска платформы, зарегистрированные базы и найденные исходники, а затем добавляет отдельную конфигурацию в `.vscode/launch.json`, не удаляя существующие.

   Порядок работы мастера:

   1. **Платформа.** Мастер ищет установленные версии и показывает только каталоги, где есть и клиент `1cv8c`, и сервер отладки `dbgs`: `%ProgramFiles%\\1cv8\\<версия>\\bin` в Windows, `/opt/1cv8/<версия>` в macOS, типовые `/opt/1cv8` и `/opt/1C/v8.3/...` в Linux. Другой каталог можно указать вручную; перед продолжением он будет проверен. На macOS `1cv8.app` не подходит: нужен серверный каталог `/opt/1cv8/<версия>`.
   2. **Информационная база.** Мастер читает стандартный список запуска 1С `ibases.v8i` и даёт выбрать базу мышью. В новой или пустой папке можно нажать **«Выбрать файл ibases.v8i…»** и указать список запуска из любого расположения: его базы появятся в том же списке для выбора. Основной каталог запуска — `%APPDATA%/1C/1CEStart` в Windows и `~/.1C/1cestart` в macOS/Linux; мастер также читает перечисленные в соседнем `1cestart.cfg` (UTF-8 или UTF-16) общие списки `CommonInfoBases`. Старые расположения остаются fallback. Имя записи используется только при выборе: мастер записывает в конфигурацию собственный аргумент запуска 1С — `/F /абсолютный/путь/к/базе` или `/Sсервер\база`, без логина и пароля. Также можно выбрать незарегистрированный каталог файловой базы или ввести `/Sсервер\база` вручную.
   3. **Исходники и расширения.** Выберите корень основной конфигурации с `Configuration.xml`. Затем мастер запускает Конфигуратор выбранной платформы в пакетном режиме `DESIGNER /DumpDBCfgList -AllExtensions` для выбранной базы. Команда только читает список расширений; временный файл результата удаляется. Для каждого расширения из базы мастер предлагает подходящий каталог исходников по имени `Properties/Name`, позволяет выбрать иной каталог и не даёт сопоставить разные имена. Если Конфигуратор недоступен или команда не сработала, доступен ручной выбор исходников расширений.
   4. **Режим, авторизация и подтверждение.** Выберите запуск либо подключение. Для запуска файловой базы мастер отдельно предлагает обычный клиент 1С (`launchMode: "client"`, временный `dbgs`) или автономный сервер (`launchMode: "standaloneServer"`, локальный `ibsrv`). Во втором режиме мастер предлагает транспорт тонкого клиента: по умолчанию прямой TCP/IP (`standaloneServerTransport: "direct"`), который запускает `1cv8c /S` и не зависит от HTTP-страницы входа; при необходимости можно выбрать HTTP (`"http"`, `1cv8c /WS http://127.0.0.1:<порт>`). В обоих вариантах запускается именно тонкий, а не веб-клиент. Он создаёт собственные данные сервера в `.vscode/onec-standalone-server`, использует выделенный порт прямого подключения и останавливает сервер с отладочной сессией. SSH не включается: для отладки он не нужен и на macOS/Linux требует отдельного ключа хоста. Для запуска можно указать пользователя: мастер запишет `userName` и защищённый VS Code-запрос пароля (`${input:…}`), а не сам пароль. Затем выберите адрес сервера отладки и подтвердите просмотренную конфигурацию.

   В multi-root workspace сначала выбирается папка, в которой будет создан `launch.json`. Поиск исходников идёт только внутри неё; внешний каталог можно добавить через **«Выбрать каталог…»**. Мастер не записывает пароль, строку подключения с учётными данными или трассировку. Сохранённые настройками запуска 1С учётные данные остаются в `ibases.v8i` и не отображаются.

4. Либо создайте `.vscode/launch.json` вручную, например:

   ```json
   {
     "version": "0.2.0",
     "configurations": [
       {
         "name": "1C: Launch",
         "type": "onec",
         "request": "launch",
         "rootProject": "/absolute/path/to/unpacked-configuration",
         "platformPath": "/absolute/path/to/1c-platform-versions",
         "platformVersion": "LATEST",
         "infoBase": "/F /absolute/path/to/file-infobase",
         "userName": "Developer",
         "password": "${input:onec.debugger.password}",
         "extensions": [
           "/absolute/path/to/unpacked-configuration-extension"
         ]
       }
     ],
     "inputs": [
       {
         "id": "onec.debugger.password",
         "type": "promptString",
         "description": "Пароль пользователя 1С",
         "password": true
       }
     ]
   }
   ```

Не устанавливайте одновременно это расширение и оригинальный `vsc-onec-debug-adapter`: оба регистрируют `type: "onec"`.

`rootProject` всегда указывает на каталог исходников основной конфигурации с `Configuration.xml`. Каждый путь в `extensions` должен указывать на корень исходников одного расширения, также содержащий `Configuration.xml`; имя в `Properties/Name` этого файла должно совпадать с именем расширения, установленного в информационной базе. Адаптер отклонит повторяющиеся пути и одинаковые имена расширений, чтобы точки останова не сопоставлялись неоднозначно.

Для `attach` тоже указывайте `rootProject`: без него подключение возможно, но адаптер не сможет надёжно сопоставить BSL-файл с модулем в базе, поэтому точки останова и переход к исходнику не гарантируются. В `attach` не нужны `platformPath` и `platformVersion`, так как сервер отладки уже запущен.

На macOS для `launch` выберите каталог установленной серверной части платформы, обычно `/opt/1cv8/<версия>` (например, `/opt/1cv8/8.3.27.1508`), содержащий `1cv8c` и `dbgs`. `1cv8.app` и его `Contents/MacOS` — GUI-пакет; в нём этих программ нет, поэтому он не подходит для запуска отладки.

## Совместимость с VS Code

Расширение регистрирует тот же тип отладчика — `"type": "onec"`, — что и [akpaevj/vsc-onec-debug-adapter](https://github.com/akpaevj/vsc-onec-debug-adapter). Поэтому конфигурации сохраняют `rootProject`, `platformPath`, `platformVersion`, `infoBase`, `debugServerHost`, `debugServerPort`, `extensions` и `autoAttachTypes`; меняется только установленное расширение. Вместо `dotnet` оно запускает подходящий для ОС нативный бинарник из VSIX.

Не устанавливайте оба расширения одновременно: оба владеют типом `onec`. Для разработки до первого release VSIX задайте путь к локальному бинарнику через настройку `onec.nativeAdapterPath`.

Для серверной базы укажите в `infoBase` строку `/Sсервер\база` (в JSON обратный слэш экранируется: `"/Sсервер\\база"`). Адаптер передаст её тонкому клиенту как есть и использует часть после обратного слэша как RDBG-псевдоним; `infoBaseAlias` нужен только чтобы явно переопределить этот псевдоним.

Файловую базу не нужно добавлять в общий список 1С: для `launch` в `infoBase` укажите `/F /путь/к/базе`. Адаптер передаст путь клиенту отдельным аргументом `/F`, поднимет временный `dbgs` и использует обязательный для файловой базы RDBG-alias `DefAlias` автоматически. Это не требует прав администратора и не меняет `ibases.v8i` пользователя.

Для авторизации при запуске укажите `userName` и `password`: они передаются тонкому клиенту как `/N` и `/P`. Рекомендуется `password: "${input:…}"` с `promptString`/`password: true`, как в примере выше: пароль не остаётся в файле. Литеральный пароль тоже поддержан для автоматизированного окружения, но он будет доступен в `launch.json` и в аргументах запущенного процесса, поэтому для обычной работы его не используйте.

## Замер задержек отладчика

Чтобы исследовать задержки F10/F11 и загрузки переменных, добавьте в нужную конфигурацию запуска `"trace": true`. По умолчанию адаптер запишет JSONL в `.vscode/onec-debug-latency.jsonl` под `rootProject`; для отдельного пути укажите `traceFile`. Когда `trace` не задан или равен `false`, файл и каталог не создаются.

```json
"trace": true,
"traceFile": "/tmp/onec-debug-latency.jsonl"
```

Каждая строка содержит `schemaVersion`, монотонный `tsMs`, `event` и поля корреляции (`traceId`, `threadId`, `targetId` или `pollId`). В трассе есть DAP-запрос/ответ шага, вызов RDBG, жизненный цикл long-poll, остановка с call stack, а также evaluate/variables и отложенный `exprEvaluated`.

## Замер производительности BSL

Во время активной сессии отладки откройте в панели **Запуск и отладка** раздел **Замеры производительности**. Нажмите `+`, выберите подключённую цель 1С, выполните интересующий сценарий в тонком клиенте и нажмите `■`. Платформа вернёт построчный результат, который появится в этом разделе и прямо в открытых BSL-модулях.

Результат содержит число вызовов, общую и чистую длительность, а также сигнал серверного вызова. Значения длительности отображаются в единицах, которые возвращает сама платформа 1С: адаптер их не пересчитывает в миллисекунды. Платформа может прислать данные по нескольким подключённым целям; строки, для которых исходник не сопоставлен с `rootProject`/`extensions`, намеренно не показываются.
